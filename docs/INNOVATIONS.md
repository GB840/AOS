# AOS 创新点深度解析

本文档对 AOS（Agent Operating System）的五大核心创新进行技术深度解析。
每个创新点包含学术背景、AOS 落地实现、与系统其他模块的协作关系。

---

## 一、因果世界模型

### 1.1 背景：Pearl 因果之梯

Judea Pearl 在 2019 年《The Book of Why》中系统化了因果推理的三层阶梯：

- **第一层：关联（Association）** — "看到 X 与 Y 同时出现"，对应统计相关性。
- **第二层：干预（Intervention）** — "若我主动做 X，Y 会怎样变化"，对应 do(X) 操作。
- **第三层：反事实（Counterfactual）** — "若当初没做 X 而做了 Z，结果会如何不同"。

传统的 AI 系统停留在第一层：模型从历史数据中学习关联模式，但无法回答"换一种做法会怎样"。
这对 AOS 的路由决策构成了根本性限制——当某个引擎失败时，系统只能凭经验猜测"换一个试试"，
而非基于可复核的证据推断"换哪个更好、好多少"。

### 1.2 AOS 落地：CausalModel 类

AOS 通过 `kernel/causal.py` 中的 `CausalModel` 类将因果推理引入路由决策。

核心数据结构是 `Intervention`（干预记录），每次路由的成败都是一条可计数的干预样本：

```python
@dataclass
class Intervention:
    context: str     # 任务/能力上下文（如 "web.search"）
    action: str      # 采取的动作/引擎（如 "anysearch" / "bing"）
    outcome: bool    # 是否成功（真实闸门判定）
    value: float     # 可选量化指标
```

关键设计约束：**所有估计必须来自可计数样本**。样本量低于 `MIN_SAMPLES=5` 时，
方法不会报一个假精确的比率，而是诚实返回 `verdict: "unknown"`。
这直接体现了理念 9「可验证即真理」——没有足够证据就不下结论。

### 1.3 核心方法

**effect_of（干预认知，第二层）**：

给定 `(context, action)` 对，计算成功率并输出 Wilson 95% 置信区间。

```python
result = model.effect_of("web.search", "anysearch")
# {
#   "success_rate": 0.78,
#   "ci_low": 0.62, "ci_high": 0.89,
#   "confidence": "medium",   # 区间宽度决定置信级别
#   "verdict": "reliable",
#   "inference_type": "observational_association"  # 诚实声明：这是观测相关，非已证因果
# }
```

为什么用 Wilson 而非 Wald 置信区间：Wald 在极端比率（如 0/1 或 1/1）下会产生越界值
（小于 0 或大于 1），Wilson 区间在小样本下更稳健。

为什么诚实声明"观测相关"：路由成败吸收了大量未控混淆变量（prompt 复杂度、模型版本、
时段、负载），CausalModel 做的是 Pearl 之梯第一层关联的量化，而非严格的 do-intervention。
这种诚实让上层决策者（autopilot 反思）知道证据的局限性。

**counterfactual（反事实认知，第三层）**：

比较"实际用 A"与"若换做 B"的差异，输出成功率差（delta）和效用差（utility_delta）：

```python
result = model.counterfactual("web.search", "anysearch", "bing",
                               costs={"anysearch": 0.1, "bing": 0.0})
# {
#   "delta": -0.05,          # bing 成功率低 5%
#   "utility_delta": +0.12,  # 但 bing 免费，效用反而更高
#   "verdict": "alt_better"  # 次优成功率但更省成本
# }
```

这是决策论层的关键：成功率最高的引擎未必是最优选择。引入成本权重后，
系统可以在"次优成功率但更省成本"和"最高成功率但更贵"之间做有据可依的权衡。

**best_action（决策论层）**：

在候选动作中按效用函数选最优：

```
utility = rate * 成功率 - cost * 成本 - latency * 时延
```

支持自定义 scorer 函数、权重配置、以及各引擎的相对成本和时延数据。
所有候选引擎样本不足时返回 None，绝不瞎选。

### 1.4 与 autopilot 反思闭环的融合

`autopilot.py` 中的 `_causal_reflection_hint` 函数将因果模型接入反思链路：

1. 每步路由结果通过 `_feed_distiller` 喂进 `EvolutionDistiller`（白盒蒸馏器）。
2. 反思时，`_causal_reflection_hint` 从蒸馏器构建 `CausalModel`。
3. 对失败能力，用 `best_action` 在成功率 x 成本 x 时延带权下选最优引擎。
4. 用 `counterfactual` 给出可复核的证据（delta / utility_delta / Wilson CI）。
5. 样本不足（候选 < 2 或任一方 < MIN_SAMPLES）诚实返回 None，不编造建议。

数据流闭环：Trace -> 蒸馏器 -> 因果模型 -> 反思建议 -> 新 Trace。

### 1.5 Wilson 95% 置信区间详解

Wilson 区间的公式为：

```
center = (p_hat + z^2/(2n)) / (1 + z^2/n)
margin = z * sqrt(p_hat*(1-p_hat)/n + z^2/(4n^2)) / (1 + z^2/n)
CI = [center - margin, center + margin]
```

其中 `p_hat = success/n`，`z = 1.96`（95% 置信度）。

与 Wald 区间相比：Wald 在 `n` 小或 `p` 接近 0/1 时产生不合理结果。
Wilson 区间始终在 [0, 1] 内，且对小样本更保守（区间更宽），
符合"不确定就显式说出来"的 AOS 诚实原则。

## 二、白盒进化蒸馏

### 2.1 背景：与 HyperAgents 黑盒改源码的对比

HyperAgents 等系统采用"黑盒进化"：直接修改自身源代码来适应新任务。
这种方式存在根本性问题：

- **不可回退**：改了源码就难以撤销到某个已知的好状态。
- **不可解释**：为什么改这一行而非那一行？进化路径是黑盒。
- **不可审计**：出了问题无法追溯是哪次"进化"引入的。
- **破坏性风险**：修改运行时代码可能导致系统整体崩溃。

AOS 选择"白盒进化"：**不改代码，改路由偏好**。
进化发生在决策层（选哪个引擎），而非执行层（改代码逻辑）。

### 2.2 AOS 做法：EvolutionDistiller 从 Trace 蒸馏引擎可靠性

`kernel/evolution_distiller.py` 中的 `EvolutionDistiller` 类实现了白盒蒸馏：

**数据采集**：`ingest(trace)` 和 `record_outcome(capability, engine, ok)` 两种方式
分别支持批量 Trace 导入和运行时增量喂样本。每条样本都是真实路由的成败判定。

**蒸馏产出**：`distill()` 方法识别不可靠引擎——满足两个条件：
1. 样本量 >= 5（`MIN_SAMPLES`，确保统计显著性）
2. 失败率 >= 50%（`SINK_FAIL_RATE`）

满足条件的引擎被标记为 `sink`（建议沉底）。

**持久化**：蒸馏结果可落盘 JSONL 文件，进程重启后经验不丢失。
热路径写入经节流（`SAVE_INTERVAL_SEC = 30` 秒），避免每条请求都重写整份文件。

### 2.3 沉底机制

"沉底"是一个**软偏好**，而非硬阻断：

- 高失败率引擎被排到路由列表末尾，而非直接移除。
- 理由：失败率是基于历史样本的统计量，可能因环境变化而改变。
  硬删除会导致系统永远失去使用该引擎的机会。
- 蒸馏结果通过 `reliable_engines()` 和 `distill()` 两个接口暴露，
  由 FabricHub 的路由层消费，调整候选引擎排序。

### 2.4 闭环：Trace -> 蒸馏 -> Registry 回读 -> 路由偏好 -> 新 Trace

完整闭环流程：

1. **Trace 生产**：autopilot/FabricHub 的每步路由产生结构化 Trace（成功/失败/引擎/错误信息）。
2. **蒸馏器收集**：`EvolutionDistiller.record_outcome()` 从路由热路径增量收集样本。
3. **蒸馏分析**：`distill()` 定期运行，识别不可靠引擎，产出沉底建议。
4. **Registry 回读**：FabricHub 路由层读取蒸馏结果，调整候选引擎排序。
5. **路由偏好生效**：后续请求优先选择被蒸馏器认可的引擎。
6. **新 Trace 产生**：新的路由结果继续喂进蒸馏器，形成正向循环。

这个闭环的每一步都是可审计的：每条样本可追溯到具体 Trace，蒸馏结果可复核，
路由偏好变更可解释。这就是"白盒"的含义。

## 三、反思闭环（Meta-Trace）

### 3.1 背景：Reflexion + ReAct + 求是引擎

**Reflexion**（Shinn et al., 2023, arXiv:2303.11366）：
提出通过显式反思文本（而非仅重放失败轨迹）来提升 agent 成功率。
核心发现：显式反思比"只看失败记录"多 +8% 成功率。

**ReAct**（Yao et al., 2022, arXiv:2210.03629）：
提出"推理-行动"交替范式，让 agent 在思考后执行、执行后观察，
形成 Thought -> Action -> Observation 循环。

**浙大求是引擎**（Qiushi Discovery Engine, 2026, arXiv:2604.27092）：
在真实光学平台上端到端验证了反思范式，并提出了 **Meta-Trace 记忆**机制——
将失败教训提炼为可复用的经验片段，注入后续任务的规划中。

### 3.2 AOS 做法：autopilot 的反思闭环

`autopilot.py` 实现了完整的 Plan -> Execute -> Reflect 循环：

```
run()
  -> _plan()           # 规划：ag2/heuristic 产出步骤列表
  -> _execute()        # 执行：逐跳经 FabricHub 路由，记录真实成败
  -> _reflect_and_redesign()  # 反思：诊断根因，重设计下一步
  -> [如有新步骤] -> _execute()  # 续接执行
```

关键设计：每步有**真实闸门**。不是"跑完就行"，而是检查：
- 搜索步：返回条数 > 0
- 代码执行步：有 stdout 或真写进非空文件
- 推理步：非拒答话术且输出长度够长

空转/敷衍一律判失败，不谎报成功。

### 3.3 上下文续接：只重设计下一步，不重跑已成功的步

这是求是引擎的核心思想在 AOS 的落地。反思轮必须：

1. 把上轮已成功步的**真实产出**作为起点续接（`seed_context`）。
2. 重设计计划只产出"从失败处继续的剩余步骤"。
3. 不再重做已成功的步。

好处：省步数，且杜绝"重搜导致结果不同"的回归问题。

`autopilot.py` 的 `_execute` 方法记录成功产出到 `prior_success` 列表，
`_reflect_and_redesign` 接收 `prior_success` 作为上下文续接的基础。

### 3.4 失败教训跨任务沉淀

`_load_lessons` 和 `_save_lesson` 实现了跨任务的经验传递：

- **保存**：反思时把"失败根因 -> 修正方案"提炼成教训持久化到 JSONL 文件。
- **加载**：新任务启动时读取历史教训，注入质疑 agent 的 prompt。
- **效果**：避免重复已知失败做法。例如，如果"bing 搜索中文 query 经常超时"
  已经是一条教训，后续中文搜索任务会自动跳过 bing。

教训存储在 `_traces/reflection_memory.jsonl`，有界（只留最近 N 条），
防磁盘打满。

### 3.5 反思上限：防无限循环

`MAX_REFLECT` 根据任务复杂度动态调整：

| 关键词数 | 上限 | 场景 |
|----------|------|------|
| < 3 | 2 轮 | 简单任务（"查天气"） |
| 3-6 | 4 轮 | 中等任务（"安装依赖并测试"） |
| > 6 | 8 轮 | 复杂任务（"全链路部署并优化"） |

默认 `MAX_REFLECT = 2`（兼容引用）。`run()` 方法按任务复杂度自动覆盖。
超过上限后即使仍有失败步也不再反思，直接返回当前最好结果。

## 四、可信记忆 Hippo-Scroll

### 4.1 双轨分离

AOS 的记忆系统采用双轨架构：

**物证轨（Evidence Track）**：
- 只读追加，不可修改。
- 存储原始 Trace、真实 stdout/stderr、exit code。
- 一旦写入即不可篡改（链式哈希保护，见 `AuditTrail`）。
- 用途：事后审计、因果模型的数据源、失败复盘的证据。

**认知轨（Cognitive Track）**：
- 可演化、支持多观点。
- 存储蒸馏后的经验、反思结论、引擎可靠性评估。
- 可被新的证据覆盖（如某引擎之前不可靠，后来修复了）。
- 用途：路由偏好、反思建议、进化决策。

为什么双轨分离：物证是事实，不可变；认知是判断，可修正。
如果混在一起，认知的更新可能误删物证，导致无法审计。

### 4.2 分歧结构收纳

当多个引擎对同一任务给出不同结果时，AOS 不强制消灭不同解读：

- 每个引擎的结果作为独立样本记录。
- 因果模型的置信区间自然反映了分歧程度——区间越宽，分歧越大。
- 反思时，分歧本身就是有价值的信号：可能说明任务本身模糊，
  或某些引擎在特定子条件下表现不同。

这种设计避免了"多数投票消灭少数真相"的问题。

### 4.3 仿生新陈代谢

AOS 的记忆有生命周期，模仿生物记忆的新陈代谢：

- **日巡检**：高频使用的记忆保持热状态。
- **周巩固**：低频但有长期价值的记忆被压缩（精简摘要）。
- **软遗忘**：长期未被命中的记忆自动分层降级（完整记录 -> 摘要 -> 删除）。
- **人工复审**：敏感操作（如删除高价值记忆）触发人工确认。

区分**短期故障记忆**（快速淘汰，如"刚才网络断了"）与**长期环境偏好**（长周期保留，
如"本机用 bing 搜索最稳定"），避免误删用户固定环境配置。

## 五、三级动态路由

### 5.1 高/中/低档位

AOS 的路由策略分三个档位：

| 档位 | 目标引擎 | 特点 | 适用场景 |
|------|----------|------|----------|
| 高档（重算力） | 本地 ollama / mistralrs | 延迟高但免费，数据不出境 | 隐私敏感、离线环境 |
| 中档（云端优质） | zhipu / 云端 API | 延迟低、质量高，需付费 | 生产环境、高并发 |
| 低档（轻量兜底） | HTML 抓取 / 规则引擎 | 免费、速度快，质量有限 | 降级、快速响应 |

路由层根据能力类型、可用资源、成本约束自动选择档位。

### 5.2 策略维度

FabricHub 路由支持五个策略维度：

- **preference**：引擎优先级排序（蒸馏器产出的可靠性评估）。
- **cost**：相对成本（免费 HTML 源成本为 0，云端 API 成本更高）。
- **latency**：响应时延（本地重算力延迟高，轻量兜底延迟低）。
- **质量**：搜索结果质量 / 推理准确性。
- **learned**：从历史 Trace 蒸馏出的可靠性偏好。

因果模型的 `best_action` 方法可以在这五个维度的带权组合下做决策，
而非只看单一指标。

### 5.3 端云合作

AOS 的路由对调用方透明：

- 云端 API 可用时，优先走云端（质量高、延迟低）。
- 云端不可达（网络故障、key 过期、配额用尽）时，自动降级到本地引擎。
- 调用方（autopilot / 用户）不感知切换过程——结果格式一致，只是来源不同。
- 本地引擎用不了时，再降级到轻量兜底。

这种"端云合作"设计实现了理念 4「万物为我所用，不为任何一物所绑定」：
任何单一组件的故障都不会导致系统整体不可用。

## 创新点之间的协作关系

五大创新不是孤立的，而是相互咬合形成系统性优势：

```
  Trace（物证轨）
      |
      v
  EvolutionDistiller（白盒蒸馏）
      |
      v
  CausalModel（因果推理）
      |
      v
  autopilot 反思闭环（Meta-Trace）
      |
      v
  FabricHub 路由（三级动态路由）
      |
      v
  新 Trace -> 闭环
```

- **白盒蒸馏**为**因果模型**提供数据源（`from_distiller`）。
- **因果模型**为**反思闭环**提供决策论层证据（`_causal_reflection_hint`）。
- **反思闭环**的教训沉淀回**蒸馏器**（`_save_lesson`），形成经验闭环。
- **三级动态路由**消费蒸馏器和因果模型的产出，调整路由偏好。
- **Hippo-Scroll 记忆**的双轨分离保证了所有环节的数据可审计。

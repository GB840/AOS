# AOS 全局审视：你到底要什么 vs 现在是什么

> 这份文档是"回看全局"，不是再加代码。目的：让你一眼看懂整个方案，并看清当前仓库与你定下的铁律之间的矛盾。

---

## 0. 你最初定的铁律（一句话）

> **四个核心能力必须用真实开源项目，不能自己写；AOS 只做"集成 + 在其上提升"的那一层。**

四个能力 = 你给的 3 个真实开源器官（OpenClaw / Hermes / DeerFlow）+ 群聊编排由 AG2（AutoGen 社区分叉, MIT）真实驱动。
AOS ≠ 智能体大脑；AOS = 让这 3 个真开源 + AG2"更好一起干活"的壳。

---

## 1. 三个真实开源器官 + AG2 群聊（大白话）

| 项目 | 真实仓库 | 它实际是啥 | 对应你给的"能力" |
|---|---|---|---|
| **OpenClaw** | openclaws.io（MIT） | 常驻你机器的**网关**：把 Agent 接到微信/Telegram/Slack 等 20+ 聊天软件，用户在自己的聊天窗口里发指令 | 接入层 / 嘴+耳朵 |
| **AG2** | ag2 (AutoGen 社区分叉, MIT) | **群聊编排**：多个智能体进同一个群互相对话、辩论、拆解任务（真实驱动，替代不可达的 ClawSwarm） | 多智能体编排 / 会议室 |
| **Hermes** | NousResearch/hermes-agent（MIT，已 vendored） | **会自我进化的员工**：干完活自动从经验里提炼并改写自己的技能，越用越强 | 自进化智能体 / 学习型大脑 |
| **DeerFlow** | bytedance/deer-flow（MIT，已 vendored） | **长时项目经理**：接任务→拆→执行→反思→继续，连续跑数小时不崩 | 长时任务引擎 / 执行体 |

**关键点**：这三/四者不是竞争关系，是不同器官。OpenClaw 负责"触达用户"，AG2 负责"群聊协作"，Hermes 负责"自己变强"，DeerFlow 负责"长跑执行"。拼起来就是一个完整能干的 Agent 系统。

> **⚠️ 关系结构提醒（不是一条链，是星型）**：四者**不是线性顺序**，经典误区是把它们排成 `OpenClaw → AG2 → Hermes → DeerFlow`。正确结构是以 **OpenClaw 为中枢的星型**：
> - **OpenClaw = 接入中枢（必备）**：所有触达用户的流量都过它，必须第一。
> - **Hermes / DeerFlow = 平行的必备引擎（脑 / 体）**：真正"会思考干活"的两个 agent 引擎，**互不依赖**。一个能用的系统 = OpenClaw + 至少一个引擎。
> - **AG2 = 群聊协调层（会议室，真实驱动）**：只是"让多个引擎互相对话"的编排层，**没有引擎时毫无意义**（空会议室）。它位于引擎之上，只在你想做多 agent 协作时才需要。
>
> 所以"先建什么"的正确顺序是：`OpenClaw（接入）→ 先接一个引擎（Hermes 或 DeerFlow）→ 已是可用单 agent 产品 → 再上 AG2 做多 agent → 最后叠 AOS 提升层`。详见第 5 节图示（星型版）。

## 2. AOS 只做"提升"——那提升到底是什么（大白话：总部 / 操作系统）

AOS 不思考、不干活，它提供 4 个开源**单体都缺、但合在一起必须有**的东西：

| AOS 提升项 | 是什么 | 真实落点（已存在代码） |
|---|---|---|
| **统一记忆/状态** | 让 4 个引擎共享同一份结构化记忆，而不是各记各的 | `src/core/database/models/`（42 表 SQLModel ORM，真实外键+WAL+并发锁） |
| **安全的进化治理** | 让 Agent"安全地改自己"——沙箱+人在环+回滚（这是 4 个 OSS 都没做好的独特价值） | `src/meta_orchestrator/` |
| **平台外壳** | 健康检查、熔断、限流、通知、事件存储（单体都不管） | `src/core/platform/`（10 个模块，全真实、可插拔降级） |
| **控制台 / 合规** | 一个地方看全部、审计全部 | `src/web/`（Streamlit+FastAPI 双管理台）、`src/compliance/` |

一句话：**4 个开源是"员工"，AOS 是"公司总部+IT+HR+审计"**。员工干活，总部让他们协作得更稳、记忆共享、安全进化、可被监管。

## 3. 现在仓库的真实状态（矛盾点！）

按你的铁律，仓库里**不该有"自己写的智能体"**。但现实是：

- 自研"脑/群聊/辩论"：`src/core/brain.py`、`swarm_flow.py`、`meta_debate.py`、`negotiation.py`、`lemon_orchestrator.py`、`task_classifier.py`……
- 自研子智能体 + **300+ 角色** + 自研技能：`src/subagents/`、`src/skills/agency_roles`、`src/skills/generated`
- 自研 Hermes/DeerFlow 包装：`src/hermes/`、`src/deerflow/`
- 四个真开源被 vendored 在 `external/`（hermes-agent、deer-flow），**基本没接进去用**
- 总计 **61,548 行** Python

→ **这违反了你的铁律**。仓库目前是"自己写了一整套Agent，又把 4 个开源晾在一边"。

## 4. 上一轮那个 `fabric` 到底是什么（去魅）

我上一轮加的 `src/core/fabric/`（481 行），本意是好的、也是薄的，但**被我用黑话包装晕了你了**。拆开看它其实就三块极朴素的接线板：

- `capability.py`：一张**清单**——"每个引擎会什么"（数据，不是架构）。直接对应你 4 个项目：
  - openclaw → 接入用户
  - ag2 → 群聊编排
  - hermes → 自我进化
  - deerflow → 长时执行
- `adapter.py`：`BaseAgentAdapter`——**"怎么跟每个引擎说话"的统一接口**。4 个开源各写一个适配器插进来。
- `registry.py`：**"任务来了找谁"的路由**。比如"要触达用户"→ 找 openclaw。

它叫"能力市场"是夸张了——本质就是**接线板**：AOS 总部用它在 4 个真开源之间转接任务。逻辑没问题，但**它目前叠在那堆自研代码之上，没有解决第 3 节的矛盾**——只是又加了一层。

## 6. 真正的下一步（不是再加层，是"取代自研"）

最有生产力的事，**不是继续在 fabric 上加东西**，而是：

> **挑一个器官，删掉仓库里自研的对应版本，改成路由到真实开源。**

举例（最小可验证的一步）：
- "触达用户"：删掉自研的接入逻辑 → 接 `OpenClaw`（adapter 已写好，端点已按真实 API 填对）。
- "群聊协作"：删掉自研的 `swarm_flow.py`/`meta_debate.py` → 接 `AG2`。
- 以此类推，把 3 个器官 + AG2 一个个接真开源，最后自研代码清零。

这样 AOS 才真正变成你要求的"薄提升层"，而不是一个 6 万行的自研 Agent 系统。

## 7. 结论

- 你**看不懂**是对的：因为当前仓库自相矛盾（自研一大堆 + 开源晾着 + 又叠抽象层）。
- 你的铁律**完全成立且正确**；问题在执行走偏了（AOS 把自己写成了"脑"，而不是"总部"）。
- 修正方向不是推翻 fabric，而是**用 fabric 把自研器官一个个换成你给的 3 个真开源 + AG2**，最终 AOS 只剩"总部+接线板"。
